过去一年多，Agent 来的比想象中快得多。它从程序员手里的工具起步，没用多久就走进了每个人的日常办公。
顺着这条线往回看，大致能摸出四股力量：
1. **编码 Agent 最先成熟**：Cursor、Codex、Claude Code 这一批，程序员群体已经率先离不开它们。
2. **OpenClaw 把概念彻底带火**：“小龙虾”登顶 GitHub 星标榜，掀起一阵“全民养虾”热潮，Agent 这件事终于从极客圈普及到了更广的人群里。
3. **办公 Agent 成为大厂主战场**：腾讯 WorkBuddy、字节豆包工作、阿里千问办公纷纷抢占办公入口，盯着白领日常工作的琐碎场景。
4. **Personal Agent 开始冒头**：给个人配一台云端电脑，7×24 小时不中断地干活，强调主动性、不打扰。海外有 xAI 的 Grok Bot、Meta 的 Muse、Instinct，国内有蚂蚁的灵光、Today 等。
这几类东西有一个共同点：不是人把每一步流程画好，而是一个 Agent 带着一套 Skill，自己去干活。
不过，办公 Agent 和 Personal Agent 走的不是同一条路。办公 Agent 本质上更偏“替代人”，把人从繁琐的日常劳动里解脱出来，是把人赶出 Loop（Out of the loop）；Personal Agent 更偏“服务人”，是在 Loop 中怎么跟人更好地相处（In the loop）。Personal Agent 更有温度，未来也许人人都会有一个；但就现阶段而言，企业里最重要的还是办公与业务类 Agent。
落到企业内部，效果到底由什么决定？一层是模型，一层是 Harness。模型越来越强，搭一个 Agent 的门槛也越来越低。真正关键的，是对业务的理解——基于这种理解给 Agent 做工具，再用 Agent 去重构工作流。
## 一、 Agent 就是模型 + Harness，企业改得了的是后者
你可以把 Agent 看成跑在 Harness 之上的应用。
如果把 Agent 比作一辆跑车，**模型是引擎，Harness 则是引擎之外的一切**——轮胎、车身、后视镜、底盘、刹车等。
模型这一层，企业很难自己训练。模型进展太快、体积也大，微调成本高，就算微调了，也很难跟上变化。现实里一般要么私有化部署，要么买云厂商的服务。模型我们可以换、可以挑，但改变不了它内在的效果。对企业来说，落地的主战场是如何构建 Harness。

眼下 Harness 已经有一层生态了：
- **闭源客户端**：Claude Code、Codex，以及 Trae、WorkBuddy、Cursor 等；
- **开源客户端**：Pi Coding Agent、DeepSeek Harness、Kimi Code、Hermes 等；
- **云/服务端托管**：Claude Managed Agent、LangChain 的 Managed Deep Agent、Kimi Hosted Agents、WorkBuddy 云端模式、字节的 AgentKit 等；
- **Harness SDK**：Deep Agents、AgentScope、Pi 等（封装了构造 Harness 的一些组件，怎么拼仍然要做大量工作，难免踩坑，但好处是灵活、定制性高）。
形态上，还要先分清 Agent 跑在哪里。
客户端 Harness 是环境在本地，沙箱、文件系统、记忆、Skill 和数据都在个人电脑上。我们见到的绝大多数 Agent 都是这一类，WorkBuddy、千问办公、豆包工作都是。云端 Harness 则是环境在云上，数据、Skill、存储、沙箱也在云上，便于集中管理。较早的例子是 Manus，给个人一台虚拟机，所有东西跑在它的云上。现在还能看到第三种趋势，比如 OpenAI 最近的 Codex，可以连电脑、连手机，也可以连它自己的虚拟机，是多端协同。
对企业来说，哪种形态更合适，要回到信息化、智能化到底要做什么。这里说的“云端”，在企业语境下更准确的说法是**服务端集中式架构（比如部署在企业私有云或专属 VPC 上，而非把核心数据交给第三方公有云）**。为了沉淀知识和流程，服务端形态明显更合适。
## 二、 个人提效不等于组织提效，沉淀靠的是服务端
每个人用起来很重要，但把好的用法沉淀下来，组织才会持续积累能力。
企业过去十年的数字化，解决了结构化数据的统一管理，信息系统也能流转，但知识积累仍是瓶颈。企业真正缺沉淀的，往往是**隐性的业务知识（Know-How）**和**标准作业流程（SOP）**——也就是那些散落在员工脑子里、靠经验判断和日常习惯完成任务的方法与步骤。智能化转型是一个难得的机会，可以把这些东西沉淀下来：标准作业流程可以沉淀为 Skill，隐性业务知识可以进入企业知识库，或以 Wiki 的形式保存、连接。 所以对企业来说，最重要的目的，其实是隐性业务知识和标准作业流程的沉淀。
对照客户端和服务端两种形态，差异就很清楚了。Agent 跑在客户端，运行环境、数据、Skill、流程都由个人掌握，都在个人电脑上。它能帮个人更好地工作，但不一定适合团队或企业的知识流转、传递和沉淀。东西在个人手里，员工往往只对自己那一块工作负责，往外贡献的意愿可能也比较低。更现实的是**权限与安全问题**：企业内部业务系统的权限体系极度复杂，服务端都未必好啃，客户端就更不可能穿透和统一管控这些权限，也很难跟上层业务系统可靠打通。
跑在服务端/云端则不同。数据、知识文档和 Skill 都在服务端，企业天然能够收集到这些材料；知识、流程、Skill 可以集中在一起，便于沉淀和分享。一个团队可以沉淀出自己的 Skill 和知识库，每个人都能使用、迭代，再根据使用日志和运行轨迹不断优化。轨迹也能采集到，还可以用 AI 去优化 Skill、流程和业务知识，也更容易跟上层业务系统结合，更可靠。大厂其实也意识到了这一点，WorkBuddy、千问、Kimi、火山等都在往服务端走，慢慢地，这应该会成为企业 Agent 落地的一种共识。
企业落地 Agent，大致可以按三步走：
- **第一步：每个人用起来**。提升 AI 素养，越用越会用，在日常工作里发现好用法，写文档、做材料，省下实打实的时间。
- **第二步：好用法沉淀成 Skill**。变成团队都能用的能力，由专业团队打磨、评测，质量有底线，用一套平台统一维护，少重复踩坑。
- **第三步：融进业务系统和流程**。接入业务系统和核心数据，数据和权限统一管理，打开日常用的系统，AI 已经在里面。最理想的形态，是用户不太感觉到它的存在，它却在默默起作用，出了问题有据可查。
什么样的用法值得往下一步走？高频、多人在用、要用到核心数据、对质量或合规有要求。

![Pasted image 20261122132635](https://old-rookie.pages.dev/media/blog/04d1df38e812347056427c7eccce2caf4c546be2380e9de91ccde5789bdab812.webp)   
之前听过一段业内讨论，讲得很实在：人的认知差距是很难抹平的，不可能人人都把 Agent 用到同一个水平；更现实的做法，是让 5% 用得最好的人把优化后的结果封装成“一键自动化”，给剩下的人直接用——就像 SaaS 软件时代，很多一线员工根本不需要懂背后的业务逻辑和原理，任务就是把几个按钮点完，而 AI 落地最直接的价值，就是帮他少点几个按钮。
顺着这个现实看，企业落地客户端类 Agent 其实也就三条路：要么靠那 5% 的高手先跑出系统性的优化，其他人直接复用结果；要么靠组织培训拉一把认知和体验的下限；如果培训来不及、自己人还没长起来，就带着 FDE 进场，在业务里摸爬滚打出一条最佳实践，再交给大家用。
人终究是偏懒的，大多数非技术员工并没有太高的动力去钻研一套全新的工具和提示词。除了少数低频、非标、探索性的复杂任务需要独立工作台之外，对于绝大多数高频日常工作，由高手或 FDE 把最佳实践沉淀下来、直接融进业务系统里，减少额外学习成本，往往比把一个独立客户端丢给全员自己折腾更可行。
退一步说，即便员工个人用客户端提了效，个人提效真的等于企业提效吗？ 至少有三层现实摆在面前：
第一，**时间不会自动转换**。个人有了 Agent，确实能省下不少办公时间，但不等于企业就多了产出。比如一位业务人员定期采集、整理并上报数据，用 Agent 可以把这件事做得又快又好，准确率也可能更高，人因此省出很多时间。可省下来的时间怎样流转，能不能自动去到更有创造性的工作上，并不会自己发生。这还需要组织结构的变化，或者更接近 AI Native 的做法，中间要有一个过程。
第二，**个人提效了，沉淀往往还在个人手里**。用得再好，知识和流程也在本地，不外溢、不复用，组织就不会积累。
第三，**产出本身会贬值**。以前我们做很多文档和 PPT，作为交付或汇报的媒介。眼下做文档、做 PPT 仍是刚需，对 Agent 来说也是长循环、多步骤、还要带调研的复杂工作。投研里做研报 PPT、做汇报 PPT、写文档这类需求量确实不小。但这到底算不算高价值工作，还值得商榷。汇报主要有两个功能：传递信息，以及展示信号。当 AI 原生组织越来越扁平、工作界限越来越模糊，指令能直接触达执行层，不再需要那么多“信息搬运工”时，等基建到位、领导可以直接向 Agent 获取信息和做模拟推演，从前那些汇报工作大概率会贬值。再者，Agent 普及之后，人人都能做出不错的文档和 PPT，人均六十分，也就约等于都是零分。 短期看，用 Agent 堆出来的材料可能会通胀；长期看，组织应该借着 Agent 主动减少这类过程性、展示性的产出，回到品味和判断本身。
本质上，一个人解决问题时用到的判断，如果能帮其他人或其他 Agent 少走弯路，组织才会有持续积累的能力。如果只把 Agent 看成个人生产力工具，很快会碰到上限——很多收益要靠 AI 与企业的整合才能实现。
## 三、 上下文是护城河，但记忆要“以应用为本”
Agent 落地的护城河不是模型。用的越多，上下文积累得越多，粘性就越高。一切围绕持续积累组织或个人上下文的工作都是值得的，越早开始越好。
这里有一个值得留意的架构方向：上下文不是简单地把所有记忆物理堆在一起，而应该“以应用为本”。 应用的侧重点不同，记忆应该以应用为中心去组织合成，不是直接复用各个应用单独提取好的二手记忆，而是底层沉淀好原始素材与运行轨迹，再按需提供给不同应用去加工它真正需要的上下文。
## 四、 有平台不等于有应用：FDE 飞轮与自建还是采购
构建 Harness 的过程里，坑也不少。比如怎样提高 KV Cache 的命中率，怎样做好工具设计，怎样开发 Skill。并不是做了一个 Skill、用上就好。Skill 需要不断打磨，要评测效果到底怎样——十次里七八次抽卡成功，恐怕还不够，里面总有不合理的地方，需要持续进化。观测同样非常重要：如何对 Harness 的轨迹做观测、做评估、做资产化，这些都要考虑。企业内部应该有一个统一的解决方案，把这些事情通盘想清楚。
即便建好了、甚至买好了 Harness 平台，也不等于就有了 Agent 应用的交付能力。平台之外，还要根据实际业务需求去做适配，去做效果优化，这部分工作量一直都在。这也是 FDE 被越来越多提起的原由。
FDE 有一个前提：必须先有一个可复用的工作平台。工程师围绕这个平台做事，发现新问题，再反过来完善平台，这样才有生命力。否则就只是人力外包，维护成本会很高，人员也不稳定，那也不叫 FDE。对企业内部的 AI 人员来说，我们本质上也是在做 FDE。
落地过程包括需求的收集整理、产品设计、Skill 或提示词的调优、MCP 工具的开发封装，以及结果出来之后的效果优化。这是一个要循环转动的飞轮，过程中会不断涌出新需求，也可能对 Harness 平台提出新的要求。项目里收集到的需求，共性的部分应当沉淀回 Harness 平台，个性的部分往往留在应用本身；构建出来的 Agent 应用，还要跟业务系统打通，比如以 API 的方式，或以个人助理的形象植入业务系统。这些都要靠 FDE 去落实。无论 FDE 由内部 AI 团队来做，还是由云平台厂商来做，都是一样。如果购买的是云端 Harness，后续费用一定不可或缺，使用过程中厂商要持续跟进。

把这些想清楚了，再来讨论 **Harness 到底该自建，还是采购**，才会比较扎实。
当然，这件事没有放之四海而皆准的答案，缺少技术团队和研发能力的企业，确实不一定适合自研。但**对于有一定规模技术团队、尤其是具备一定自研能力的企业，我更倾向于认真考虑自建**，原因有三点：
1. **构建软件的门槛变低了**：2026 年以来，软件开发变得越来越容易、越来越便宜。开发模式在变扁平，以前要几十上百人做的软件，现在一个小团队配上 AI Agent 也能做出不错的产品。我们不必妄自菲薄，很多核心技术其实能够掌握。
2. **技术远未收敛，Harness 反而在变厚**：大模型能力越来越强，并没有让 Harness 变薄，新特性需求反而不断涌现——比如 Personal Agent 带来的异步执行需求，以及 DeepSeek 提出的 Super-agent 双层架构原型。AI 平台类标品的迭代速度未必能跟上这种变化节奏。FDE 要求平台持续进化，个性化修改需要反哺回平台，如果自己不掌握，就只能等厂商排期，而 ToB 厂商有没有意愿和精力持续投入，要打一个问号。
3. **私有化部署的基建对接账**：哪怕外采标品平台，只要落地到企业私有化部署，依然绕不开对接企业内部的存储、沙箱、网络和运行环境，这部分工作量一点也不小。企业内部的技术团队天然熟悉自家基础设施，从设计之初就能把现有底座考虑进去，反而少走很多适配的弯路。
落到具体选型上，更务实的做法是**分层掌控**：
- **模型层**：外采或私有化部署，不自研基座；
- **通用底座/SDK**：借力开源生态（如 AgentScope、Deep Agents 等）做定制组装，避免从零造轮子；
- **核心编排、Skill 资产与上下文层**：重点自建与自主掌控，把私有流程、隐性业务知识和 FDE 迭代闭环留在自己手里。
## 五、 写在最后：奔着“AI 驱动”去，给年轻人让路
最后补三点关于组织和人的想法，作为一名一线工程师的观察，它们往往比技术本身更决定成败：
1. **AI 引发的组织变革已经在发生了**。工具变了，协作方式、信息流转和岗位分工都会跟着松动、重组。
2. **把“AI 驱动业务变革”当作目标，跳出“AI 赋能”的固有思维**。如果只是把 AI 当作旧流程上的补丁，天花板很低；只有奔着重构业务去想，才能应对未来的变化，真正发挥 AI 的价值。
3. **AI 队伍最宝贵的资产是年轻人**。现在做大模型和原生应用的主力已然是年轻人了，他们包袱少、对新范式更敏感。作为老人，最重要的是培养年轻人，给合适的年轻人让路，给他们更大的舞台，创造更多的机会。
